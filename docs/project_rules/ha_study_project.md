# HA-STUDY 프로젝트 방향 및 개발 원칙

## 1. 프로젝트 정의

**HA-STUDY는 단일 스터디카페 지점용 예약 프로그램이 아니다.**

스터디카페 브랜드와 여러 지점을 하나의 시스템에서 관리하고, 향후 예약·이용·키오스크·매출·통계·운영 분석까지 통합할 수 있는 **멀티테넌트 스터디카페 운영 플랫폼**을 목표로 한다.

첫 번째 실제 적용 대상은 **르하임 스터디카페**이며, 초기에는 지인이 운영하는 2개 지점을 대상으로 실제 운영 및 검증을 진행한다.

그러나 시스템 구조와 데이터 모델을 해당 2개 지점에 종속해서 설계해서는 안 된다.

최종적인 기본 계층 구조는 다음과 같다.

```text
HA-STUDY
│
├─ 브랜드
│   │
│   ├─ 르하임
│   │   ├─ 지점 A
│   │   ├─ 지점 B
│   │   ├─ 지점 C
│   │   └─ ...
│   │
│   └─ 향후 다른 브랜드
│       ├─ 지점 A
│       └─ 지점 B
│
└─ Platform Admin
```

즉,

**Platform → Brand → Branch → Space**

구조를 기본으로 한다.

# 2. 핵심 개발 목표

현재 목표는 기능을 많이 만드는 것이 아니다.

**첫 번째 2개 지점에서 실제 사용할 수 있는 안정적인 예약 시스템을 만드는 것이 1차 목표다.**

단, 데이터베이스와 프로그램 아키텍처는 향후 다음 기능을 추가할 수 있도록 설계한다.

* 다중 브랜드
* 다중 지점
* 다중 룸/공간
* 회원 관리
* 예약 관리
* 실제 이용 관리
* 키오스크 연동
* 결제
* 이용권/시간권
* 매출 관리
* 지점 운영 통계
* 브랜드 전체 통계
* 혼잡도 분석
* 이용 패턴 분석
* 매출 예측
* 운영 예측 및 AI 분석

**중요: 미래 기능을 현재 모두 구현하라는 의미가 아니다.**

현재 필요하지 않은 기능은 구현하지 않는다.

대신 미래 기능을 추가할 때 기존 구조를 대규모로 다시 작성하지 않아도 되도록 데이터 구조와 책임을 분리한다.

# 4. 웹 / 모바일 전략

하나의 코드베이스를 기본으로 한다.

```text
HA-STUDY
        │
        ├─ PC
        │   └─ Web
        │
        └─ Mobile
            └─ PWA
```

PC에서는 일반 웹 서비스 형태로 제공한다.

모바일에서는 반응형 UI를 제공하며 PWA 설치를 지원한다.

사용자는 앱 설치 없이 웹에서도 HA-STUDY를 사용할 수 있어야 한다.

Android 및 iPhone 사용자는 필요하면 HA-STUDY를 홈 화면에 설치하여 앱과 유사한 방식으로 사용할 수 있도록 한다.

초기 버전에서는 Google Play / Apple App Store 등록을 필수 요구사항으로 하지 않는다.

또한 APK 직접 배포 역시 초기 핵심 요구사항으로 하지 않는다.

향후 필요성이 생기면 Capacitor 등의 방식을 검토하여 네이티브 패키징을 추가할 수 있도록 한다.

# 6. 멀티테넌트 원칙

HA-STUDY는 처음부터 멀티테넌트 시스템으로 설계한다.

르하임 전용 코드 또는 특정 지점 전용 코드를 작성하지 않는다.

예를 들어 다음과 같은 코드/데이터 구조를 만들지 않는다.

```text
leheimRoom
leheimUser
leheimReservation

room1
room2

leheimBranch1
```

대신 범용 도메인 개념을 사용한다.

```text
brand
branch
space
user
customer
reservation
usage
```

현재 룸이 2개라고 하더라도 `ROOM1`, `ROOM2`를 프로그램 구조에 하드코딩하지 않는다.

공간은 데이터로 추가/수정/비활성화할 수 있어야 한다.

# 8. 예약과 실제 이용의 분리

`예약`과 `실제 이용`은 동일한 개념으로 처리하지 않는다.

예:

```text
예약
14:00 ~ 16:00

실제 입실
14:07

실제 퇴실
15:42
```

따라서 장기적으로 다음 개념을 분리할 수 있도록 한다.

```text
Reservation
≠
Usage Session
```

이를 통해 향후 다음 데이터를 분석할 수 있어야 한다.

* 예약 시간
* 실제 이용 시간
* 입실 시간
* 퇴실 시간
* 예약 취소
* 노쇼
* 공간 점유율
* 시간대별 이용률

# 9. 키오스크 확장 원칙

향후 키오스크는 HA-STUDY와 별개의 시스템으로 만들지 않는다.

키오스크 역시 HA-STUDY 플랫폼에 접속하는 하나의 Client로 취급한다.

```text
                 HA-STUDY CORE
                       │
          ┌────────────┼────────────┐
          │            │            │
      Customer       Manager       Kiosk
       Web/PWA         Web           UI
          │            │            │
          └────────────┼────────────┘
                       │
                    Backend
                       │
                    Database
```

따라서 모바일 예약, 관리자 예약, 키오스크 현장 예약이 서로 다른 데이터베이스를 사용해서는 안 된다.

모든 예약 및 이용 데이터는 HA-STUDY의 동일한 핵심 데이터 모델을 기준으로 처리한다.

현재 사용 중인 외부 키오스크 시스템과의 실제 연동 가능 여부는 해당 시스템의 API 제공 여부 등을 확인한 후 별도 판단한다.

API 연동이 불가능할 경우 향후 HA-STUDY 자체 키오스크 개발도 고려할 수 있다.

# 10. 권한 구조

향후 다음과 같은 권한 계층을 지원할 수 있도록 설계한다.

```text
PLATFORM_ADMIN
HA-STUDY 전체 관리자

BRAND_ADMIN
브랜드 전체 관리자

BRANCH_OWNER / BRANCH_ADMIN
개별 지점 관리자

STAFF
지점 직원

CUSTOMER
일반 사용자
```

기본 원칙:

* HA-STUDY 관리자는 전체 플랫폼을 관리할 수 있다.
* 브랜드 관리자는 해당 브랜드의 지점들을 관리할 수 있다.
* 지점 관리자는 자신의 지점 데이터만 접근할 수 있다.
* 일반 고객은 허용된 공개 데이터와 자신의 데이터만 접근할 수 있다.

프론트엔드에서 메뉴를 숨기는 것만으로 권한을 처리하지 않는다.

실제 데이터 접근 권한은 Supabase RLS 등을 이용해 서버/DB 수준에서도 통제한다.

# 11. 데이터 수집 및 향후 분석

HA-STUDY는 단순 예약 프로그램을 넘어 향후 운영 분석 플랫폼으로 확장할 수 있도록 한다.

따라서 장기적으로 다음 데이터를 축적할 수 있도록 고려한다.

```text
예약
취소
노쇼
입실
퇴실
실제 이용시간
결제
매출
공간별 이용률
시간대별 이용률
요일별 이용률
회원 이용 패턴
키오스크 이용
```

이 데이터가 충분히 축적되면 향후 다음 기능을 추가할 수 있다.

* 시간대별 혼잡도
* 공간별 점유율
* 지점별 이용률
* 지점별 매출 비교
* 재방문 분석
* 이용 패턴 분석
* 매출 추세
* 혼잡 예상
* 향후 매출 예상
* 운영 개선 추천

초기 버전에서 AI 예측 기능을 구현하지 않는다.

**먼저 정확한 데이터를 축적할 수 있는 구조를 만드는 것을 우선한다.**

# 12. 이벤트 및 변경 이력

예약, 이용, 결제 등 주요 운영 이벤트는 향후 추적 및 분석이 가능하도록 변경 이력 또는 이벤트 로그 구조를 고려한다.

입실

다만 구체적인 로그 구현은 기존 프로젝트의 Logging/8-Atom 규칙에 따라 결정한다.

# 13. 디자인 시스템 원칙

HA-STUDY의 모든 화면은 동일한 제품처럼 보여야 한다.

바이브코딩 과정에서 페이지별로 서로 다른 디자인이 생성되는 것을 허용하지 않는다.

디자인 관련 구현은 공통 `05_design_system.md` 규칙을 반드시 따른다.

HA-STUDY 프로젝트에서 확정되는 실제 디자인 값은 프로젝트 전용 Design Rule에서 관리한다.

여기에는 향후 다음 항목이 포함될 수 있다.

```text
Color
Typography
Font Size
Spacing
Radius
Shadow
Breakpoint
Component Style
Responsive Rule
```

페이지에서 임의의 디자인 규칙을 새로 만들어 사용하지 않는다.

기존 공통 UI Component가 있다면 반드시 재사용한다.

필요한 UI가 존재하지 않는다면 특정 페이지에 독립 스타일을 만드는 것이 아니라 공통 Design System 확장 여부를 먼저 검토한다.

---

# 14. UI 구현 핵심 원칙

**페이지는 디자인하는 곳이 아니라 공통 UI를 조립하는 곳으로 취급한다.**

예:

```text
Design Token
      ↓
Common UI Component
      ↓
HA-STUDY Pattern
      ↓
Page
```

버튼, Input, Card, Modal, Table 등의 기본 요소를 페이지마다 새롭게 구현하지 않는다.

향후 예약 카드, 공간 카드, 상태 표시, 페이지 헤더, 검색/필터 영역 등 반복되는 HA-STUDY 패턴 역시 공통 컴포넌트화한다.

# 15. 반응형 원칙

HA-STUDY는 동일한 서비스이지만 사용 목적에 따라 화면 경험을 다르게 구성할 수 있다.

### 고객

모바일 우선.

빠른 예약 및 예약 확인을 중심으로 한다.

### 지점 관리자

PC Web 사용성을 중요하게 고려한다.

예약 현황, 회원, 매출, 통계 등을 넓은 화면에서 효율적으로 관리할 수 있도록 한다.

관리 기능 역시 필요하면 모바일에서 사용할 수 있어야 한다.

### 키오스크

향후 키오스크 전용 레이아웃을 별도로 제공할 수 있도록 한다.

# 16. 개발 우선순위

전체 플랫폼을 한 번에 구현하지 않는다.

### Phase 1

르하임 2개 지점에서 실제 사용할 수 있는 예약 시스템.

### Phase 2

회원 및 실제 이용 관리.

### Phase 3

키오스크 및 결제/이용권 연동.

### Phase 4

운영 및 매출 대시보드.

### Phase 5

축적된 데이터를 이용한 분석 및 예측 기능.

각 Phase는 이전 Phase의 실제 운영 결과를 기반으로 확장한다.

---

# 17. 가장 중요한 개발 원칙

HA-STUDY 개발 시 다음 기준을 항상 유지한다.

**1. 르하임 전용 프로그램으로 만들지 않는다.**

**2. 특정 지점에 종속된 코드를 작성하지 않는다.**

**3. 현재 필요한 기능과 미래 확장을 구분한다.**

**4. 미래 기능을 미리 전부 구현하지 않는다.**

**5. 하지만 미래 확장을 막는 데이터 구조를 만들지 않는다.**

**6. 모든 지점과 브랜드가 동일한 HA-STUDY Core를 사용한다.**

**7. 웹, PWA, 관리자, 향후 키오스크가 동일한 핵심 데이터를 사용한다.**

**8. 예약 데이터와 실제 이용 데이터를 구분한다.**

**9. 운영 데이터를 장기적으로 축적할 수 있도록 설계한다.**

**10. 디자인은 페이지별로 만들지 않고 공통 Design System을 따른다.**

**11. 기존 8-Atom 및 프로젝트 SSOT 규칙을 최우선으로 준수한다.**

**12. 구현 전에 기존 문서, 프로젝트 색인, DB Schema, 프로젝트 특수 지침을 확인하고 기존 구조를 임의로 우회하지 않는다.**

# 18. 프로젝트 최종 방향

HA-STUDY의 장기적인 목표는 다음과 같다.

> **HA-STUDY는 스터디카페 브랜드와 각 지점의 예약, 공간, 고객, 실제 이용, 키오스크, 결제 및 운영 데이터를 하나의 플랫폼으로 통합하고, 축적된 데이터를 이용해 지점 운영 현황과 향후 운영 판단을 지원하는 멀티테넌트 스터디카페 운영 플랫폼이다.**

첫 번째 목표는 거대한 플랫폼을 완성하는 것이 아니다.

**르하임 2개 실제 지점에서 기존 시스템보다 편리하고 안정적으로 사용할 수 있는 HA-STUDY v1을 완성하는 것이 첫 번째 성공 기준이다.**

이후 실제 사용 결과를 기반으로 다른 르하임 지점 및 다른 브랜드로 단계적으로 확장한다.
